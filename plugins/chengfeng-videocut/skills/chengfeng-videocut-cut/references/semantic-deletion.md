# 语义删除规则

## 接入与传输优先级

先完整读取并遵守[共享接入规则](../../../references/plugin-access.md)与主 Skill 第 0 步。
用户指定已有工作台时，[已有工作台接入](../../../references/existing-workflow.md)覆盖本文件所有
`runtime_cli` 命令示例：同一 connection/projectId 使用 `runtime_playback` 读取、
`runtime_cuts_put` 提交，并以 `runtime_project` 读回 workflow、cuts、edit-list。
下文 argv 只适用于另行选定且通过门禁的受管路线，不会跟随 connection；缺能力即停止，
不回退 canonical 5190、service ensure、旧 runtime_cli 或源码 CLI。语义方法与人工审核不因传输变化而省略。

## 最高原则

```text
前一次不完整 / 错误表达  -> 删除
后一次完整 / 正确重说    -> 保留
```

默认删前保后。不要用“较短的一句”替代这个顺序规则，除非用户明确指定保留前版。

## 判断之前：稿子必须按播放顺序铺平

**这是识别质量最大的单一变量，比判据本身更要紧。**

判断「有没有重复」靠的是前后相邻，而相邻指的是**播出来相邻**，不是文件里存着相邻。剪过的项目里，
源片上隔 40 秒的两句话在成片里可能紧挨着；源片上紧挨着的两句中间可能还留着内容。

**必须用 Product 提供的视图，不许自己拼：**

```bash
调用 MCP `runtime_cli`：`{"argv":["transcript","playback","<项目目录>","--json"]}`
```

它按播放顺序铺平成一条流，`removedSpeech` 标出此处原本说过话、已删除、不会播出。
返回里的 `note` 字段是这份输入的读法，判断前先读它。

**为什么不许自己拼**（2026-07-26 实测，两次都拼错了）：

```text
错法一   按原始段落分组、保留原始段号
         剪过之后段号必然跳号（0121 -> 0124），判断者把跳号读成
         「中间有 3.47 秒没给我看，所以不能判」——而那 3.47 秒正是已删内容
         后果：两条正确判断被否决，其中一条是一眼可见的重复

错法二   把被压掉的停顿也标成「此处删过内容」
         标记从 15 个涨到 58 个，判断者以为整篇到处断裂
         后果：普遍变保守、宁可不删
```

两次的共同点：**判据没错，输入撒了谎，而且是静默的。** 输入格式改变的是结论，不只是呈现。

## 先句段，后逐词

先由唯一协调者串行读完同一版本的全部 playback 页面，检查索引连续和 transcript/edit-list
revision 一致，直到 `nextCursor=null`；中途版本变化则丢弃全部句段与逐词记录，从第一页重读。
完整逐词流适合确定具体删除词，第一层先用句段识别相隔很远的重录：

```text
同一 revision 的完整 playback stream
  → 临时句段索引：扫完整体、建立重复组、判断每组保哪一遍
  → 剩余完整逐词流：保留 gap / removedSpeech / 播放断点，五轮确定语音 wordIds
  → 重复组与五轮记录去重、自读校验 → 唯一全量提案 → 一次 CAS
```

按已有标点、明显停顿和播放断点组织句段，保留每段首尾 `wordId`、播放顺序和时间。
句段索引只用于当前任务阅读，不写项目文件，不形成第二份播放状态；首尾 ID 不代表可以按
编号范围猜出整段词，最终必须回到真实 stream 展开为准确的语音 `wordIds`。

先扫完全部句段，再找重复组：同一表达任务说了几遍、每遍完整性、前后差异、保哪遍、删哪遍。
不能只比较相邻句；结构、叙事作用和上下文相同的远距离句子也可能是多次 take。
关键词不同不自动证明两句独立，也不自动证明重复：后一次修正前版时删前保后并标高风险；
各有独立信息时两句都留。整句、长段、关键名词变化、同开头后半分叉一律高风险，不能因文本
完全相同就跳过整句级上下文复核。

进入逐词层后，只临时跳过已拟删整段的语音词，仍保留拟删段位置、gap、`removedSpeech` 和
播放断点；不把拟删段伪装成 Product 已删事实。第一轮回读重复组、核对保留版并落实精确词 ID，
后四轮依次精修剩余完整流。若撤销整段候选，恢复的词必须补过五类检查再汇总，不能成为漏扫区。
这些阅读记录都不能单独提交；协调者合并重叠、解决冲突，按删后播放顺序通读全文，读不通就撤销。

## 候选类型

- 句间重复：两次表达同一意思，删除前一次。
- 句内重复：只删前面的重复片段，保留后续完整句，不能顺手删整句。
- 残句与改口：删除前面的残句、错误数字或错误专名，保留完整重说。
- 英文卡壳：识别英文词头、字母或音节重复，不只匹配中文。删前保后的语义选择成立，
  不代表第一遍尾音已删净或第二遍词头完整；提交后须将这些接缝纳入声音边界复核。
- 语气词：单个自然语气词保守保留；连续无意义语气词可作为一组低风险候选。
- 有口播稿：只用于语义对齐与纠错，不能逐字 diff，也不能补入视频没说的话。

类型与五轮扫描的对应：第 1 轮吃「句间重复 + 句内重复」，第 2 轮吃「残句与改口」，
第 3 轮吃「口误重说（错数字/错专名）」，第 4 轮吃「英文卡壳」，第 5 轮吃
「语气词与口头禅」。每轮只带本轮判据；第一轮还要核对句段层重复组。

## 判例

格式固定四行：原文（播放顺序）→ 删 → 剩下读作 → 为什么。
R1–R6 来自 2026-08-03 grok 项目实录（【】内为删除部分）。

**R1 · 多次重录整句（第 1 轮，高风险）**

```text
原文：现在很少刷叉了【因为今天有什么值得研究已经被我外包给了】【因为今天有什么值得研究已经被我外】【因】为今天有什么值得研究已经被我外包给了Codex和Grok
删：前两遍不完整的起头
剩下读作：现在很少刷叉了，因为今天有什么值得研究已经被我外包给了Codex和Grok
为什么：同一句起头录了三遍，删前保后只留最后完整遍。整句级删除必须高风险复核，
并进重复句子表（说了几遍、保哪遍）
```

**R2 · 句内重复（第 1 轮，低风险）**

```text
原文：给我做一份AI日报【最近我就关心】最近我就很关心剪辑
删：最近我就关心
剩下读作：给我做一份AI日报。最近我就很关心剪辑
为什么：前一遍是不完整起头，后一遍完整；只删前面重复片段，不顺手删整句
```

**R3 · 卡壳碎片连缀（第 2 轮，低风险）**

```text
原文：给了一篇AI日报给我【我看一眼就能看】【就能】我看一眼就能看到他和
删：连续两个不完整起头
剩下读作：给了一篇AI日报给我，我看一眼就能看到他和…
为什么：连续多个残句碎片视为一组，全删，保最后完整一遍
```

**R4 · 分叉重说（第 2 轮，高风险）**

```text
原文：【多数Agent能搜到的网页】多数Agent它能搜出网页但Grok…
删：第一遍
剩下读作：多数Agent它能搜出网页，但Grok…
为什么：同开头、后半分叉 → 高风险复核。两遍信息相同取后一遍；
若两遍各有独立信息，都保留——那不是重复，是补充（此时不列为候选）
```

**R5 · 错专名的那一遍（第 3 轮，高风险）**

```text
原文：【比如我就让他跟踪】【比如我就让Gokul跟踪Codex团队他就找到了…它就能找到】比如我让grok跟踪
删：前两遍（含把 Grok 听成 Gokul 的那遍）
剩下读作：比如我让grok跟踪…
为什么：错专名 + 改口，保说对的那遍。被删遍里的错专名不用管；
保留遍里的错专名必须在修字环节先改对——删词修不掉听错的字
```

**R6 · 单个语气词不删（第 5 轮，反例）**

```text
原文：这个功能呢它其实…
删：（不删）
剩下读作：原样
为什么：单个自然语气词保守保留，删了语气就假了。只有连续无意义语气词
（≥2 个连缀）才作为一组低风险候选；密度与容忍度以用户偏好文件为准
```

**纠正类判例暂缺**：2026-08-03 首个复盘项目用户全盘采纳（提案 242 处零修改），
还没有「用户否掉 AI」的真实判例。今后每次交棒复盘，被用户恢复或补删的案例
经确认后按同一格式入库。

## 风险

| 风险 | 例子 | 动作 |
| --- | --- | --- |
| 低 | 完全包含的前置重复、三字以内连续口头禅 | 可初始化为删除 |
| 高 | 整句、长片段、同开头但后半分叉、专名或数字改口 | 必须复核上下文，见下 |

**「复核上下文」是 AI 自己再看一遍，不是拿去问用户。**

高风险只改变**判断要多严**，不改变**结果长什么样**。复核的做法是回到播放顺序的稿子把前后念一遍、
确认删的是靠前那一版、确认删完读得通；确认不了就**不列为候选**。

删除只有「删除 / 未删除」两态。高风险候选不得变成「建议删除，等用户点头」——那是第三态，
产品已明确否决。人的审核发生在**提交之后**：用户在文稿上看划线，自己决定恢复哪些。

```text
不要   逐条问用户「这条要删吗」
不要   把候选标成「待确认」交上去
要     自己复核完，该删的直接进 cutWordIds，不该删的丢掉
```

## 提交：每次交完整结论，不是增量

`cuts set` 的语义层是**替换**语义，不是累加：Product 用「停顿基线 ∪ 本次提交」重建删词集合。
所以提交里必须包含**本轮判断的全部结论**，不只是这一轮新找到的。

继续旧项目时，当前 Product Cuts/reasons 与上次留存的全量提案一起用于核对：仍有效且未被
有意撤回的已确认语义删除，和本轮新增选择合并；`removedSpeech` 不等于应恢复，已被人工恢复的
词也不能根据旧提案再删。不盲拷含停顿基线的全部 `cutWordIds`，不读取/手工拼入
`initialization.baselineCutWordIds`。缺少可区分的语义选择或当前理由时，先报告具体缺口，
不能假设旧选择为空，也不能伪造旧理由。整段候选若撤回，恢复的词需补完五轮检查。

2026-07-26 实测的后果：第二次只交了新找到的两处，上一轮四处的记录被挤掉，删词数从 430 掉到 394。
声音仍然正确（手工时间线只会被挖、不会被恢复），**但账本退了，而且 `changed: true` 看着一切正常**。

`cuts set` 现在会在结果里报 `noLongerCut`——本次不再删的词数与样本。**提交后必须看这个字段**：
不为零且不是有意撤回，先核对是否误交增量，不直接再次写入。需要修正时按当前版本完整重读、
重审后再形成新全量提案。未知结果或 `noLongerCut="unknown"` 不授权重提：按共享合同查回原
operationId 和输入，不换 ID；CAS 冲突使旧候选失效，不偷换 revision 硬覆盖。

显式 connection 下先用 `runtime_project` 只读当前 cuts/workflow/edit-list；当前桥没有专门的
cuts operation 查询工具。只有当前值吻合不能证明原 operation 已成功；无法唯一确认时报告
“提交结果待核实”，不编造查询接口，不以再次 `runtime_cuts_put` 代替查询，不自动重试。

每个候选都绑定稳定 `wordIds`、类型与风险；不要用数组位置、文本行号或时间近似替代 wordIds。

## 理由会被记下来

`reasons` 已经落盘（2026-07-26 起）：每组词带 `kind` 与 `risk`，存在 Cuts 里。
当前形状为 `{wordIds: string[], kind: 非空字符串, risk: "low" | "high"}`；`kind` 不限于
示例的 `repeat`，按真实类型填写，不发明必需枚举或使用 `medium` 风险。实际提供者若合同不同，先核对。

两条性质由 Product 保证，Skill 不用自己维护：

- 理由不会比它解释的删除活得久——词被恢复，理由自动消失
- 理由里提到没被删的词，那部分会被裁掉；形状不合法直接报错

所以理由要如实写。**界面目前不显示它**，但它是「为什么删这一句」唯一的记录。

## 停顿与新接缝：目标不等于已验证事实

普通静音不是语义删除候选。保留 playback 的全部 gap 证据，提案只提交真正要删的语音
`wordIds`；不把 gap ID 塞进 `cutWordIds` 强压停顿，不临场猜刀口毫秒数，不手改 EDL，
不生成独立音轨或额外平滑版音频。相邻静音合并与刀口计算属于 Product 的版本化策略。

自然停顿 `<=300ms` 原样保留是产品策略目标。只有实际服务支持并执行对应策略，且回读的
参数确实为 `0.3 / 0.08 / 0.16` 时，才可按以下含义核对：自然停顿保留上限
`300ms`；语义删除后新接缝上一保留词后最多 `80ms`、下一保留词前最多 `160ms`，
合计最多 `240ms`。这是有条件的参数说明，不是每次 `cuts set` 都调用该规划器的保证，
也不证明当前 connection 的 build 已包含并走通此路径；不能据此断言长停顿必定“删除中段”。

验收以当前实际策略、同版本 Cuts/EDL 与 Product 回读为准，核对真实播放区间和接缝。
gap 是否出现在 `cutWordIds`、文稿是否有删除线，都不能单独证明这段声音已经删除或停顿已正确。
仅有 revision 证明状态版本，不证明具体停顿处理正确；缺 EDL 证据、缺能力或结果不一致时明确
报告未验证/阻塞，不手工修时间线补齐。API 回读与实际人耳试听分层报告；单样本偏好不代表跨项目最优。

## 边界冲突与声音复核

**检查对象是剪后的新接缝，不只是被划掉的文字。** 比较提交前后的同源 EDL，确定本次实际
变化的源入出点；若策略重算影响多处，不能只查用户指出的一处就报整体通过。对重复、重录及
英文卡壳，区分删除侧尾音残留、保留侧词头截断、停顿叠加与单纯点击声，不能用同一种淡化处理。
比较基线来自本轮保存的提交前 Product 回读或其版本化变更回执；前版缺失时报告“本次变化
范围未知”，只陈述已检查的具体位置，不以现有片段总数推算本次变化或宣称全覆盖。

先发现当前 Product 是否提供受支持的边界诊断/对齐入口，再按其实际合同调用；不虚构工具名、
参数或成功字段。现有 `runtime_project` 的 Cuts/EDL 回读及 `runtime_playback` 本身不提供
声学通过证明。入口缺失时仍可报告已提交账本与结构检查、打开同版本人工审核，但声音检查须
明确未完成，不把“没有诊断结果”写成“没有异常”；不得绕过接入合同拼脚本写项目。

有诊断能力时，核对返回结果绑定的源身份、EDL revision、检查接缝范围及未解决项。已有但
过期的报告、波形图或别处的测试不能代替本轮结果；记录检查总数、实际覆盖数和未检查范围。
没有声学结果时这些覆盖数不得冒充已完成声音检查。peak/RMS、采样跳变只支持定位和排序，
不是音素识别、听感结论或自动改刀依据。
机器诊断用描述性摘要呈现：源身份、EDL revision、检查范围与已检查/总数（未知就写未知）、
未解决项、人耳听审状态。不新增项目字段或总质量 PASS；“机器报告无异常”必须限定到其版本
和覆盖范围，不能替代 human listening。

遇到以下任一证据，停止该处自动调整，保留最后已提交的项目状态并说明冲突：

- 安全搜索范围内没有合格安静点，算法回退原切点且仍有未解决的声音异常；
- 继续消除疑似尾音需要越过下一保留词的标注起点；
- 原音频/受支持诊断与词时间标注明显不符，或用户指出残音、截字后尚未完成对应复核。

报告“该接缝需要时间对齐/声音复核”，并注明已证实部分与尚待确认部分；这是诊断描述，
不写入新的项目状态、删除第三态或未经支持的字段。时间标注有误的怀疑不是改时间的权限：
不能猜毫秒数、改 transcript 时间或 EDL、扩大全局搜索上限、恢复旧删词来掩盖问题，也不能
让播放器另改刀口。若已有正式对齐能力，先核对它的授权、费用与版本合同；没有则报告缺口，
不重新付费转录、不替换服务。查出问题不等于已修复。

用户反馈残音/截字后，将当时版本、稳定词ID（若可取得）、实际区间和验证证据记录在本轮
任务汇报中；用户要求落盘时，只使用明确的非受管说明文档，不自造 Product 资源、状态文件
或写入未知字段。未取得的值不得推测。修复后先复测原反馈位置，再检查本次改动影响的同类接缝，
保留尚未通过的项。没有真实人类听审只报告机器检查与覆盖范围，不要求用户替代可自动完成的
第一轮检查，也不声称完整听感通过。
